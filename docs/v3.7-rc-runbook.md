# V3.7 RC controlled acceptance runbook

This runbook remains **NOT RUN** until a dedicated Panel 3.4.4 and Telegram
bot are available. Keep tokens in the host's private `.env`; do not put them
in commands, test files, issue comments or shared logs. Back up the project
volume before upgrading. See the [backup procedure](../README.md) and
[interactive UI checklist](v3.7-rc-ui-checklist.md).

## 1. Read-only Remnawave smoke

Confirm the deployed Panel image or Panel UI reports **3.4.4** before any
request. Use the production `services/panel_api.py` wrappers and the
[API inventory](remnawave-api-inventory.md). Record only method, path, HTTP
status and whether the documented `response` schema validated. Do not record
the body, token, username, subscription URL or IP address.

| Method | Path | Expected contract shape | Status |
|---|---|---|---|
| GET | `/api/system/health` | `GetRemnawaveHealthResponseDto` | NOT RUN |
| GET | `/api/system/stats` | `GetStatsResponseDto` | NOT RUN |
| GET | `/api/system/stats/recap` | `GetRecapResponseDto` | NOT RUN |
| GET | `/api/nodes` | `GetNodesResponseDto` | NOT RUN |
| GET | `/api/internal-squads` | `GetInternalSquadsResponseDto` | NOT RUN |
| GET | `/api/external-squads` | `GetExternalSquadsResponseDto` | NOT RUN |
| GET | `/api/config-profiles` | `GetConfigProfilesResponseDto` | NOT RUN |
| GET | `/api/subscription-settings` | `GetSubscriptionSettingsResponseDto` | NOT RUN |
| GET | `/api/bandwidth-stats/nodes` | Required date query; `GetStatsNodesUsageResponseDto` | NOT RUN |
| GET | `/api/subscription-request-history` | Bounded pagination; `records` and `total` | NOT RUN |

If an existing user can be read safely, use a numeric ID selected in the
Panel and additionally check `GET /api/users/{userId}`, accessible nodes and
user subscription request history. Stop on a contract mismatch; confirm the
Panel version and sanitize the response before recording a defect.

## 2. Controlled writes

Real writes are **SKIPPED** unless an operator has explicitly set
`REMNASHOP_RC_ALLOW_WRITE_TESTS=1` on the dedicated RC test host. Use one
user marked `remnashop_rc_<timestamp>`, no real customer binding or payment.
Follow create → numeric ID → get by ID and username → patch → disable →
enable → reset traffic → metadata → read nodes/history → delete → confirm
absence by GET. Stop after a failure and record the test marker and numeric
ID for manual cleanup. Never retry an uncertain delete blindly.

## 3. Telegram and Docker runtime

Use Docker Compose only. Before startup, ensure another instance is not
polling the same bot token. Inspect `docker compose -p remnashop ps`, health
and sanitized logs long enough to rule out immediate exits, restart loops,
`Unauthorized`, `Conflict`, `InvalidToken`, schema errors and scheduler
duplicates. If `Conflict` appears, stop **only the RC instance**; do not
stop an unknown production poller. Restart the RC container once and verify
config, SQLite and pending jobs are preserved. Then work through the
[UI checklist](v3.7-rc-ui-checklist.md).

## 4. Fresh install, update and uninstall

Run these only on a disposable Debian/Ubuntu host or equivalent safe Linux
target. Fresh install: empty target → bootstrap → private `.env` input →
Compose build/start → repeated healthy checks. Existing update: back up the
stopped V3.6 volume first; then bootstrap update, compare local record counts,
settings and `PRAGMA integrity_check`, and verify repeated health checks.

For uninstall acceptance, deploy a dedicated test instance and create
separately named dummy container, volume and network. Test interactive
confirmation and project-scoped deletion, then confirm the dummy resources
still exist. Never run destructive uninstall acceptance against a production
deployment. The offline RC audit exercised backup/restore commands against a
disposable Docker volume and verified an unrelated test volume remained
untouched. The full installer, runtime update and uninstall workflows remain
**NOT RUN** until that isolated host is available.
